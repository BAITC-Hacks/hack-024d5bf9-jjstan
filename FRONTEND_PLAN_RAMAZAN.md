## 3. Какие данные используешь

### Сначала: синтетический пример

Сделай 6–10 товаров по формату из `TEAM_PLAN.md`, а не произвольный JSON. Нужны разные состояния:

- обычный заказ, например расчёт 70 → 72 с округлением;
- достаточный остаток и нулевой заказ;
- риск дефицита;
- ожидаемая поставка;
- отмеченная разовая аномалия;
- отсутствующий актуальный остаток;
- два поставщика, чтобы проверить фильтр и группировку.

`demo_data.py` возвращает тестовые входные данные и, пока engine не готов, подписанные демонстрационные результаты того же контракта. В UI постоянно видно «Демонстрационные данные». После готовности engine тестовый набор тоже пропускается через настоящий расчёт.

## 4. Какие экраны делаем

Одно приложение: боковая панель и три вкладки. В верхней части — название StockPilot, дата расчёта и статус источников. Светлый фон, один основной цвет, красный для ошибок, жёлтый для ограничений; значения статусов дублируются текстом.

### Боковая панель — ввод и настройки

- Режим: демонстрационные / реальные данные.
- Загрузка ZIP/XLSX.
- Дата расчёта, согласованная с датами источников.
- Срок поставки отдельно для каждого поставщика.
- Период между пересчётами и страховые дни категорий.
- Переключатели аномалий и stockout.
- Кнопка «Рассчитать заказ».

Не выдавай неизвестный срок поставки за подтверждённый. Отсутствующие интервалы stockout должны сопровождаться понятным сообщением. Настройки меняются в форме; дорогой расчёт запускается по кнопке, а не от каждого изменения фильтра.

### Вкладка «Заказы»

Сверху: количество позиций к заказу, срочных позиций и позиций с проблемами данных. Не суммируй штуки и метры в один показатель и не показывай стоимость закупки без подтверждённых закупочных цен.

Таблица:

| Поле на экране | Источник |
|---|---|
| Поставщик | `supplier` |
| Код и название | `sku`, `name` |
| Единица | `unit` |
| Свободный остаток | `free_stock` |
| В пути на горизонте | `incoming_in_horizon` |
| Рекомендовано | `recommended_qty` |
| Количество к утверждению | UI-поле `approved_qty` |
| Срочность | `urgency` |
| Причина | `reason` |
| Качество данных | `data_quality` |

Добавь поиск по SKU/названию и фильтр по поставщику. Редактируются только количество к утверждению и выбор строк. Остальные поля доступны для чтения.

Кнопки: «Утвердить выбранные позиции» и «Скачать утверждённый заказ». Рядом явно показывай количество выбранных строк и поставщиков. Фильтр не должен незаметно менять состав утверждаемого заказа.

### Вкладка «Объяснение SKU»

Выбор товара, график истории и прогноза, список исключённых аномалий, дата остатка, ожидаемые поступления, числовые слагаемые формулы и причина округления. Исторические месячные продажи и дневной прогноз перед показом приводи к сопоставимой частоте; неполные месяцы помечай.

Расчёт берётся у Гапара. Если нужной детализации нет в контракте, согласуй дополнительное поле; не создавай вторую версию алгоритма ради карточки.

### Вкладка «Данные»

Загруженные файлы, дата источников, число обработанных товаров, таблица `quality_report` и `diagnostics`. Для пустого результата, загрузки, ошибки, устаревшего остатка и отсутствующего engine предусмотрены отдельные понятные состояния.

## 5. Как подключаем тиммейтов

```python
from data_loader import load_data
from engine import calculate_orders

dataset = load_data(paths)
result = calculate_orders(dataset, settings)

orders = result["orders"]
forecast = result["forecast"]
anomalies = result["anomalies"]
diagnostics = result["diagnostics"]
```

Точные поля таблиц и настроек уже записаны в `TEAM_PLAN.md`. Не переименовывай их для русских заголовков — русские названия задаются при отображении.

**От Нурасыла нужно:** loader, совместимые таблицы, даты и статус актуальности остатков, сообщение о пропусках.

**От Гапара нужно:** engine, стабильные четыре таблицы результата, причины расчёта, пример с известным ответом.

До готовности модулей UI работает с явно обозначенной заглушкой. Отсутствие конкретного модуля можно обработать отдельно; любые внутренние ошибки импорта нельзя скрывать общим fallback на демо.

## 6. Состояние, утверждение и экспорт

Streamlit перезапускает скрипт при взаимодействии с элементами. Сохраняй результат расчёта, ручные количества и утверждение в `st.session_state`.

Правки храни по `(supplier, sku)`, не по номеру строки. При фильтрации и сортировке проверяй соответствие редактора стабильным ключам: сам факт использования `data_editor` не решает перенос правок между строками.

Состояния заказа: **нет расчёта → черновик → утверждён → экспортирован**. Изменение исходных файлов, параметров расчёта или ручного количества отменяет прежнее утверждение. Пока новый расчёт не выполнен, старый результат помечается как устаревший и не утверждается.

Перед утверждением проверяй неотрицательность, конечность числа, единицу и допустимость количества для товара. Минимум/кратность проверяются по правилам поставщика. Не округляй все товары до целого: для части единиц могут быть дробные количества. Проверку исключений из правил согласуй с командой; молча не пропускай.

Строки `data_quality="insufficient"` не включай в утверждённый заказ до устранения обязательных пропусков. Нулевое ручное значение допустимо как отказ от закупки позиции и не заменяется рекомендацией автоматически.

CSV: поставщик, код 1С, артикул поставщика при наличии, название, единица, утверждённое количество, исходная рекомендация, причина. Используй UTF-8 с BOM для удобства открытия кириллицы в Excel. Для внешних текстовых полей предотврати интерпретацию строк как формул при открытии в таблицах. Экспорт содержит снимок утверждённых данных, а не заново рассчитанные значения.

Состояние сессии не является постоянной базой: после перезапуска оно может потеряться. Подготовленный заказ пользователь скачивает. CSV с кодом 1С не называем готовой интеграцией с 1С без проверки формата импорта.

## Новые обязанности в текущем этапе

- Явный поставщик неоднозначного XLSX передаётся через безопасную временную папку; выбор входит в идентификатор расчёта.
- `ai_assistant.py` и `tests/test_ai_assistant.py` принадлежат Рамазану. Два сценария, строгий ответ с evidence_id, ограниченный контекст и таймаут; без свободного чата, новых серверов и БД.
- Ключ OpenAI хранится только в env/secrets. Модель выбирается явно и проверяется через API. В unit-тестах сеть заменена mock.
- Числа берутся из engine, AI только выбирает пояснения и вопросы. Неизвестное количество не становится допустимым после AI.
- Смена входов/поставщика очищает пояснения и отменяет старое утверждение. Смена AI-модели очищает только AI-кэш.
- Условия склада/MOQ подтверждаются явно. Нет действия «игнорировать все ошибки».
- NVIDIA Brev не обозначается как подключённый inference; реальные средства/купон не подтверждены, coupon-ссылка не сохраняется.
