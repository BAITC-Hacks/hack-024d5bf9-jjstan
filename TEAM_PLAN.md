# StockPilot — общий план команды на 5 часов

> Нурасыл — данные. Гапар — бэкенд и расчёты. Рамазан — фронтенд и интеграция.
> Этот файл — общий договор команды: кто что делает, что передаёт другим и что должно работать к концу каждого часа.

## 1. Что создаём

**StockPilot — помощник закупщика:** загрузка выгрузок 1С → прогноз регулярного спроса → рекомендации заказов поставщикам → объяснение каждой позиции → правка и утверждение менеджером → экспорт.

Данные: архивы **Systeme electric.zip** и **IEK.zip**. Первый сквозной сценарий собираем на Systeme Electric, затем подключаем IEK. Синтетические примеры используем для ранней интеграции и проверки возможностей, для которых в реальных данных не хватает полей; всегда обозначаем их как тестовые.

**Стек:** Python, pandas, openpyxl, numpy, Streamlit, pytest. Одно локальное приложение. Фронтенд на Streamlit напрямую вызывает Python-функции бэкенда. Отдельный HTTP API за эти 5 часов не нужен.

**Результат:** приложение, рекомендации по двум поставщикам с явными ограничениями данных, объяснения, CSV-экспорт утверждённых количеств, тесты, README и почасовая история Git. XLSX-экспорт — если основная версия готова.

## 3. Общий контракт модулей

В первые **15 минут** все подтверждают этот контракт и маленький синтетический пример. Нурасыл и Гапар сразу работают с ним, Рамазан строит интерфейс на тех же полях. Полная готовность реальных данных не должна блокировать остальных.

```python
dataset = load_data(paths)                     # Нурасыл
result = calculate_orders(dataset, settings)   # Гапар
orders = result["orders"]                      # Рамазан показывает и редактирует
```

### Вход: `load_data(paths: list[str]) -> dict[str, pandas.DataFrame]`

`paths` — локальные пути к ZIP-архивам или распакованным XLSX. Путь с компьютера другого участника не предполагается существующим.

| Таблица | Обязательные колонки |
|---|---|
| `products` | `supplier, sku, supplier_article, name, category, unit, min_order_qty, pack_multiple` |
| `monthly_sales` | `supplier, sku, month, quantity, is_complete` |
| `transactions` | `supplier, sku, date, document_id, customer_id, warehouse, quantity, transaction_type` |
| `stock` | `supplier, sku, warehouse, as_of, free_stock, is_current` |
| `transit` | `supplier, sku, warehouse, expected_date, quantity` |
| `seasonality` | `supplier, category, month_number, factor` |
| `stockouts` | `supplier, sku, warehouse, start_date, end_date` |
| `quality_report` | `supplier, sku, severity, issue, source` |

Правила:

- `supplier`: `Systeme Electric` или `IEK`; `sku` — строка.
- Даты — pandas datetime; `month` — первое число месяца; числовые пропуски — `NaN`, неизвестные даты — `NaT`.
- Недоступная таблица — пустой DataFrame с обязательными колонками.
- `customer_id` отсутствует → null, а не номер накладной.
- `category="__all__"` в сезонности — общий профиль поставщика.
- `warehouse="__all__"` — подтверждённый общий контур складов. Неизвестный склад — null и запись в отчёте качества.
- Нормализованные продажи положительные, возвраты отрицательные. `transaction_type` различает операции.
- `is_current=False` запрещает молча выдавать исторический остаток за текущий.
- Месячная таблица и динамика представляют одну историю: их нельзя складывать между собой.
- Дополнительные поля разрешены, переименование обязательных — только после согласования.

### Настройки `settings`

| Поле | Значение |
|---|---|
| `as_of` | Дата расчёта |
| `lead_time_days` | Словарь `{supplier: число дней}` |
| `review_period_days` | Период между пересчётами в днях |
| `safety_days_by_category` | Словарь `{category: число страховых дней}` |
| `default_safety_days` | Страховые дни по умолчанию |
| `exclude_anomalies` | Включено ли исключение разовых аномалий |
| `restore_stockouts` | Включено ли восстановление спроса при известных stockout |

Сроки поставки и страховые дни при отсутствии подтверждённых значений — видимые настройки прототипа, а не факты о поставщике. Неизвестные обязательные параметры нельзя молча придумывать.

### Выход: `calculate_orders(dataset: dict, settings: dict) -> dict`

| Таблица | Колонки |
|---|---|
| `orders` | `supplier, sku, name, category, unit, stock_as_of, free_stock, incoming_in_horizon, forecast_qty, safety_stock, raw_order_qty, recommended_qty, urgency, reason, data_quality` |
| `forecast` | `supplier, sku, date, predicted_qty` |
| `anomalies` | `supplier, sku, date, document_id, quantity, excluded, reason` |
| `diagnostics` | `supplier, sku, severity, issue` |

`forecast` содержит дневной прогноз на горизонт. `reason` собирается из фактического расчёта. `severity`: `info`, `warning`, `error`. `urgency`: `urgent`, `normal`, `none`, `unknown`. `data_quality`: `ok`, `warning`, `insufficient`.

При нехватке обязательных данных: `recommended_qty=NaN`, `data_quality="insufficient"`, причина в диагностике. Рамазан не включает такие строки в утверждённый заказ без устранения причины и пересчёта.

`approved_qty` и состояние утверждения принадлежат UI. Рамазан привязывает изменения к ключу `(supplier, sku)`, чтобы сортировка и фильтры не переносили правки на другой товар. MVP предполагает один согласованный контур складов; расчёт по каждому складу требует отдельного расширения ключей и контракта.

## 4. Расчёт и особенности исходников

```text
H = срок поставки + период между пересчётами
Q0 = max(0, прогноз спроса на H + страховой запас
            − свободный остаток − поступления внутри H)

Если Q0 = 0 → заказ = 0.
Иначе → применить минимальное количество и округлить вверх до кратности.
```

Пример для теста: прогноз 140, страховой запас 20, свободный остаток 50, транзит 40 → потребность 70. При минимуме 24 и кратности 12 → заказ **72**.

- **Systeme Electric:** файл транзита содержит также свободный остаток, категории и коэффициенты. Это первый сквозной сценарий. Из свободного остатка резерв повторно не вычитается.
- **IEK:** месячные остатки обозначены как начальные. Текущий заказ требует актуального снимка или подтверждённого ввода менеджера. В транзите даты есть в заголовках; для бухт/метров нужна проверка единиц.
- **Знаки:** нельзя применять `abs()` ко всем количествам: возвраты могут превратиться в продажи.
- **Периоды:** неполный сентябрь 2026 не сравнивается с полным месяцем как равный период.
- **MOQ:** кратность и минимальное разрешённое количество не обязательно совпадают.
- **Аномалии:** оцениваем размер и повторяемость сделки; устойчивый рост не исключаем как разовый выброс. Выявление нескольких заказов одного клиента на реальных файлах ограничено отсутствием ID клиента.
- **Stockout:** месячные остатки не дают точных дней отсутствия. Полный сценарий проверяем на явно синтетических интервалах. Исторический упущенный спрос корректирует прогноз, но не прибавляется целиком к новому заказу.
- **Сезонность и рост:** коэффициенты проверяются; не учитываем один тренд дважды и не используем отрицательный прогноз спроса.
- **Категории:** числовой код категории сам по себе не определяет важность; связь со страховыми днями задаётся явно.
- **Транзит:** поставка после возникновения дефицита не устраняет риск до её прибытия.

## 6. Git: прогресс каждого участника каждый час

| Участник | Рабочая ветка |
|---|---|
| Нурасыл | `feat/data` |
| Гапар | `feat/engine` |
| Рамазан | `feat/ui` |

Все работают в своих клонах/каталогах одного репозитория. `main` должен запускаться. Первый push — в начале проекта; далее каждый участник пушит содержательные изменения не реже раза в час.

1. **До :45 каждого часа:** каждый заканчивает небольшую часть, просматривает diff, делает commit и push своей ветки, передаёт краткий статус.
2. **:45–:55:** Рамазан интегрирует готовые PR; вместе исправляем конфликты и проверяем запуск/затронутые тесты.
3. **До :59:** Рамазан пушит `main`, добавляет тег этапа `h1`…`h5` и запись в `docs/progress.md`. Неготовые изменения остаются в рабочей ветке с указанием причины.

Пример для Гапара; выполнять из своего репозитория после настройки remote:

```bash
git status
git diff
git add engine.py tests/test_engine.py docs/methodology.md
git diff --cached
git commit -m "feat: calculate orders with incoming deliveries"
git push origin feat/engine
```

Добавляем только существующие проверенные файлы. Не делаем пустые коммиты ради активности, не используем force-push в общие ветки. Исходные коммерческие Excel, `.env`, ключи и кэш не включаем в публичный Git; для воспроизводимости добавляем синтетический пример и инструкцию загрузки.
